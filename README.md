# HBR 战斗助手

给 Heaven Burns Red（炽焰天穹）国服 PC 端做战斗数值工具：**实时抓帧 → 读出伤害 → 算数值**。

> 📘 **要接手这个项目，先读 [`HANDOVER.md`](HANDOVER.md)** ——
> 那里有完整的环境说明、HBR 国服的实测事实、**每个坑的根因**、
> 以及**已经证伪、不用再试的方向**。本文只讲怎么用。

分成三层，各自解耦，中间用 JSON 交接：

| 层 | 包 | 干什么 | 依赖 |
|---|---|---|---|
| **看画面** | `hbr_capture` | 实时盯着游戏窗口，按需 / 按事件自动截帧 | 纯标准库 |
| **看懂画面** | `hbr_recog` | 从帧里读伤害数字和标签 | numpy + Pillow（+ RapidOCR 可选）|
| **算数值** | `hbr_calc` | 伤害统计、Boss DP/HP 推演、超频条计算 | 纯标准库 |

```powershell
# 只有识别层需要装东西。默认源在国内可能 403，用镜像更稳。
F:\python\python.exe -m pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

## 快速开始

### 挂件（推荐）

双击 **`启动挂件.bat`**。

它用 `pythonw.exe` 启动，**完全不出现控制台窗口**，所以不会有东西挡住游戏。
挂件是一个窄长条（默认 280×960），自动贴在游戏窗口右边。

**不需要 `--match`** —— 游戏窗口是自动识别的，判据是窗口类名 `UnityWndClass`。
国服的游戏和启动器**进程名一模一样**（都叫 `HeavenBurnsRed.exe`），只看进程名会认错，
启动器的类名是 `CGameLauncherWnd`。

| 按钮 / 热键 | 作用 |
|---|---|
| **开始 / 停止** | 开关抓帧 |
| **抓一帧** | 立刻存一张当前画面（不用切窗口） |
| **F9** | 全局热键，等同"抓一帧" |
| **F10** | 全局热键，停止 |

状态栏里的 `认出伤害` 是内容触发的命中数 —— 它一跳就说明逮到一个伤害帧。

## ⚠️ 为什么 `settle` 会漏掉绝大部分伤害帧

这是实测踩出来的大坑：跑了 48 帧，**只有 1 帧是伤害帧**，其余全是转场闪白、
指令待机这种"画面静止的瞬间"。

原因不在参数，在**触发逻辑的哲学不对**：

> `settle` 的设计目标是"等画面稳定下来再存"，而伤害数字恰恰出现在**动画过程中**。
> 等画面真的稳定了，数字往往已经消失、或者场景已经切走。

**解法是内容触发**：每抓一帧就用识别器看一眼，**认出伤害数字就立刻存**。
不依赖画面变不变，直接看内容。识别只跑伤害带，实测 **3~4 ms/帧**。

配套的几道机制：

| 机制 | 作用 |
|---|---|
| **数值去重** | 同一个数值**连续可见**多久都只存一次，见下 |
| **闪白过滤** | 亮像素 >85% 的全白帧直接丢。阈值给得高是因为改成内容触发之后，闪白帧只有"恰好认出伤害数字"才会被存 —— 它上面确实有可读数字，不该丢 |
| **尺寸自适应** | 坐标和尺寸门槛按帧宽相对 2048 缩放。窗口尺寸会变（见过 2048×1152 / 1920×1095 / 1365×768），不缩放会静默地什么都读不到 |

### 为什么伤害数字会"重复很多"

两个原因叠加，而且都不是"去重窗口开得不够大"：

1. **数字会滚动。** 出场时读数会在几帧内变化（实测 `495` → `501` 之后稳定）。
2. **切分不稳定。** 同一帧画面里的 `4238`，连续 4 帧被读出过
   `428` / `4238` / `238` / `4238` —— 位数少说明切分残缺，不是数字真的变短。

所以"看到就存"必然重复。现在**攒成一次"伤害事件"**：

| 情况 | 处理 |
|---|---|
| 数值变了（还在滚动） | 稳定性重新计时，并**保留位数最多的那次读数** |
| 数值稳住 0.8 秒 | 定稿，存这一帧 |
| 数字从画面消失 0.6 秒 | 也定稿，存缓冲里那帧 |

**判"新的一次命中"只看一个信号：数字从「看不见」变成「看得见」。**
定稿之后数字往往还挂在屏幕上，这时不能开新事件 —— 这个 bug 真写出来过，靠单测抓住的。

另外 **`settle` 触发完全不看内容**，画面一稳就会把 `damage` 存过的再存一遍
（实测一个 `1829591` 存了 3 张）。现在 `settle` 存之前会检查"这个数值是不是刚存过"。

### 为什么伤害数字会被整个漏掉（`BREAK!` 与短数字）

用户报过"还是有缺失"，查下来是**识别管线的结构性缺陷**，不是参数问题。

**问题一：`BREAK!` 覆盖层。** 它和伤害数字**竖直方向重叠**（实测都占 y 564~605），
按行投影切不开、只会粘成一行；接着按行高做覆盖率过滤时，
较矮的那一组（伤害数字 52px vs `BREAK!` 67px）会被当成"小字后缀"整个丢掉。
**实测这让 4 帧伤害完全读不到。**

更隐蔽的是 `segment_digits` 内部会**重新检测一次行**、只保留像素最多的那行 ——
于是只切出 `BREAK!`，数字连字形都没生成。

**问题二：短数字。** `min_row_pixels=40` 对 3 位数的伤害太高，行检测直接断掉；
`min_run=4` 又把 `448`、`8` 这种整行丢掉。

**解法**：改成**行 + 列两道分组**，因为它们解决的是两个正交的问题：

| 分组方式 | 解决什么 |
|---|---|
| **按行** | 把标签「合计伤害」（在数字上方）和数字分开 |
| **按列** | 把 `BREAK!`（和数字竖直重叠）和数字分开 |

只用行分不开 `BREAK!`，只用列分不开标签 —— 两个都要。

再加两道保险：

- **组内按高度再切一刀**：`BREAK!` 和数字横向间隔有时不够大，会被归成一组，
  然后高度方差检查把整组否决（连带里面读得好好的 `32774` 一起丢）
- **未识别字符比例门**：`BREAK!` 会被读成 `8????`，只要求"含数字"的话它会冒充伤害值 `8`

短数字则靠 `min_run=1` + **短串高置信度门**（1~2 位要求置信 ≥0.70；
实测真的 `8` 置信 0.94，`BREAK!` 误读出的 `8` 只有 0.52）。

结果：**24 个已知帧 24/24 全对**（含 `BREAK!` 遮挡的 3 帧、1 位的 `8`、3 位的 `448`），
且没有任何假阳性。

## ⚠️ 伤害数字上有两种标签，含义完全不同

实测发现伤害数字上方的标签有两种：

| 标签 | 含义 | 数字量级 |
|---|---|---|
| **合计伤害** | 一次动作的**总和** | 百万~千万 |
| **平均伤害** | 多目标时**按怪数平均** | 十几万 |

```
总伤害 = 平均伤害 × 怪物数
```

**把平均值当总和用会差十几倍，而且数字本身读得没错，极难发现。**
（这个坑是用户反馈"读取仍旧有问题"之后才挖出来的 —— 之前所有帧碰巧都是「合计伤害」。）

用画面证实过：`平均伤害` 的帧里**全是 2 个怪**（两个血条），`合计伤害` 的帧里是 1 个。

所以识别结果里带了 `label` 字段，批量读取时：

- 只有标签明确是 `合计` 的读数才计入总和
- `平均` 的单独列出，**不计入**
- 标签没认出来的也**不计入**（宁可少算，不可算错）

### 标签识别：优先 OCR，模板兜底

| 后端 | 条件 | 实测 |
|---|---|---|
| **RapidOCR** | 装了 `rapidocr-onnxruntime` | 12/12 全对，**21 ms/次**，置信 0.71~0.99 |
| 模板匹配 | 没装 OCR 时的退路 | 12/12 全对，但最小类间差只有 0.02，区分度太薄 |

两条路都会在**不确定时报「未知」而不是硬猜** —— 这个字段猜错差十几倍，比说不知道糟得多。

> **OCR 提速的关键：只调 `text_rec`，不走完整流程。** 标签位置是我们自己按数字框裁出来的，
> 不需要文字检测，而 `text_det` 正是耗时大头：
> `完整流程 1509 ms → 只调 text_rec 121 ms → 跳过方向分类 21 ms`。

> 模板法为什么留着：换台机器可能没装 OCR，或者装不上（公司网络等），
> 那时候整条链路还要能跑，只是标签会有较多「未知」。
> 双判据是**粉色 + 高局部对比度**（只用粉色会在火焰/粉色场景上崩，只用对比度会在水晶粒子上崩），
> 归一化用**稳健包围盒**忽略离群像素（不做这步准确率从 12/12 掉到 6/12）。

> 想用上「平均伤害」的读数，还得知道场上有几个怪（数血条）。在那之前它一律不计入。

## `watch` 的四种触发（可以同时开）

| 触发 | 开关 | 说明 |
|---|---|---|
| **damage** | `--damage-trigger` | **认出伤害数字就立刻存**。解决"伤害帧被漏掉"，见上面那一节 |
| **hotkey** | `--hotkey F9` | 按一下**立刻重抓一张当前帧**（不是缓冲帧）。不用 alt-tab，见到伤害帧就敲一下 |
| **settle** | `--threshold 0.02 --settle 0.4` | 画面变化超过阈值后，**等它停下来**再存一张。适合抓结算界面这类稳定画面 |
| **interval** | `--interval 5` | 每隔 N 秒留底一张 |

> 抓伤害帧请用 **damage**，不要指望 **settle** —— 后者等的是"画面稳定"，
> 而伤害数字出现在动画过程中，实测 48 帧 settle 里只有 1 帧是伤害帧。

## 挂件踩过的坑（都会让挂件"看起来消失"）

1. **`pythonw` 下错误是隐形的**。挂件用 `pythonw` 启动（为了不出现控制台），
   而它会把未捕获的异常**静默吞掉** —— 表现就是"双击了但什么都没发生"，完全无从排查。
   现在会弹窗 + 把 traceback 写到 `widget-error.log`。

2. **Tk 的 geometry 单位不是物理像素**。进程设了 DPI 感知之后，在这台 150% 缩放的机器上
   请求 `300x960` 实际只得到 `200x640`（差 1.5 倍）。**初始尺寸和摆位两处都要换算** ——
   只修摆位的话，游戏还没找到时窗口会小一圈。见 `Widget._dpi_factor()`。
   另外窗口边框不在 geometry 里，不留余量的话窗口右边缘会伸出屏幕（实测超出 12px）。

3. **游戏窗口最小化时 Windows 返回的矩形是 `(-32000, -32000, ...)`**。
   照着 `x = right + margin` 算会把挂件扔到 `x = -31832` ——
   **窗口还在、进程还活着，只是远在屏幕外看不见**。
   这就是"点停止再开始挂件就没了"的原因（那一刻游戏是最小化的）。
   现在最小化的窗口走单独的摆位分支，并且最后**无条件夹回屏幕内**。

4. **线程意外结束后要自动重连**。游戏窗口最小化会让抓图连续失败，
   原来失败 60 次就放弃退出 —— 现在"最小化"被当成**可恢复**状态，
   会一直等它回来；其他原因导致的线程结束也会自动重连（3 秒起，退避到 30 秒）。

5. **游戏没找到时窗口会停在系统随便挑的位置**。`_build_ui` 只设尺寸不设位置，
   而摆位只在 `_connect` 找到游戏窗口后才做 —— 游戏没开时窗口就一直待在
   系统挑的地方（实测屏幕中左 127,70）。现在 UI 建好就立刻摆一次位
   （游戏未知时贴屏幕右侧居中）。

6. **看门狗**。上面这些修完之后按理不可能再丢，但用户那边还是复现过，
   所以不再靠推理：每 2 秒检查一次，**跑到屏幕外、或者压在游戏上**就自动拉回来。
   另外有「归位」按钮可以手动叫回来。
   `widget-geometry.log` 现在**追加**并带时间戳和游戏窗口矩形，再出问题可以直接看是哪一次。

## 抓帧方法：HBR 国服只有 `screendc` 是活的

实测三种抓法的结果（这是 HBR 国服的硬事实，不是猜测）：

| 方法 | 结果 |
|---|---|
| `printwindow` | **失败**（Unity 窗口拿不到） |
| `bitblt` | 拿到的是**冻结帧** —— 画面其实在变，它纹丝不动 |
| `screendc` | **活画面** ✅ 约 100% 非黑，12~40 ms/帧 |

所以 `auto` 的顺序是 `printwindow → screendc → bitblt`，并且**带活动性自检**：
连抓两次比对，发现是冻结帧就自动切到 `screendc`。

`screendc` 要求游戏窗口**可见且没被盖住**。工具会：

- 检查游戏是不是前台窗口
- 报告有谁压在游戏上（按遮挡面积排序，列出进程名）
- 被挡住 ≥ 90% 时**直接中止**，而不是闷声存一文件夹垃圾
- 发现自己（控制台）挡住游戏时，临时最小化自己

## 帧的保存与删除

每次会话写一份 `session-<run_id>.json` 和 `session-<run_id>.log`，帧和索引
（`index.jsonl`）在同一个目录。

会话结束时挂件会**问一句「这次的帧留着还是删掉」**：

- 选**留着** → 归档到 `results/<run_id>/`，和以后的会话分开
- 选**删掉** → **走回收站**（`SHFileOperationW` + `FOF_ALLOWUNDO`），不是永久删除

> 删除走回收站是硬要求：删错了还能捞回来。
> 误删过一次 36 帧，就是用 `tools/restore_recycled_frames.py` 全部还原的。

## 游戏机制（已确认的部分）

- 单 hit 只作用于 DP 或 HP 之一，**没有溢出**
- GAUGE BREAK = 锁盾，最少保留 1 DP
- `+115.9%` 是**破坏率**，独立乘区
- 技能 1 hit = 2.5% OD，链加成 1%~15%；普攻固定 7.5%，不吃加成
- 连击珠每颗 +1 hit
- 数字颜色对应属性（金色=雷、红色=火……）
- `合计伤害` / `平均伤害` 的区分见上面那一节
